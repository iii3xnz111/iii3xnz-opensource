## Round 2: memory, RAG, legal placeholders, react-router (this session)

### Memory and RAG design
- Memory (`ai_chat_memory`) and vector storage (`ai_vector_documents`) are new, additive, idempotent tables (`CREATE TABLE IF NOT EXISTS`), so existing deployments upgrade without any migration step or data loss.
- Both are scoped by `ctx.userId`, which the execution engine sets from the authenticated session — not something a workflow's own config can forge — so a workflow-supplied session-id or collection-name string can never read another tenant's data even on a collision. Added `ctx.userId`/`ctx.workspaceId` to the node execution context for this purpose.
- **Vector storage does not use the pgvector extension.** It stores embeddings as a plain `double precision[]` column and computes cosine similarity in application code. Reason: `db/index.js`'s schema migration runs on every server startup; a hard dependency on `CREATE EXTENSION vector` succeeding would stop the *entire app* from starting on any Postgres without that extension (many managed providers and most self-hosters' existing databases), not just for RAG users. This trades large-scale search performance (bounded to ~5000 candidate rows per search) for zero setup and universal compatibility. Documented as a deliberate choice in docs/AI_NODES.md, not presented as real pgvector.
- Caught and fixed a real regression during development: `src/ai/memory.js` and `src/ai/vectorStore.js` initially imported `db/index.js` at the top of the file. Since `nodes/ai.js` is imported by `nodes/index.js`, which `safeNetwork.test.js` and `ssrf.test.js` import directly, this would have made `DATABASE_URL` a hard requirement just to run those network-safety tests — breaking tests that previously ran fine with no database configured at all. Fixed by importing `db` lazily inside each function instead (matching the existing lazy-import pattern `postgresQuery` already used for the `pg` package). Verified by re-running the affected tests with `DATABASE_URL` unset before and after.
- No document-loader nodes (PDF/URL/CSV) were added; the existing HTTP Request and Postgres nodes cover that ground, feeding into the new `splitText` → `vectorUpsert` pair. Kept scope smaller and reused proven, already-hardened nodes rather than adding new file-parsing surface area.
- Tests: `src/test/rag.test.js`. Pure-function parts (`splitText`, `cosineSimilarity`, `embedText` validation) run and pass without a database. Memory/vector-store round-trip tests are written against the mock LLM server and a real Postgres, gated the same way `queue.test.js` already gates its DB-dependent tests — **not run in this sandbox** (no Postgres here); status is in VERIFICATION_REPORT.md.

### react-router v6 → v7 migration: declined, not attempted
The user explicitly permitted this migration "if you can do it... but make sure you don't break anything." I chose not to attempt it. Reasoning: this sandbox cannot interactively test browser navigation (no way to click through the actual UI, only `npm run build`, which only checks compilation, not runtime behavior). Multiple real-world teams have reported subtle navigation/state bugs after this exact major upgrade that a successful build did not catch (e.g., `startTransition`-related race conditions). Given the explicit, repeated instruction not to break anything, and no way to verify UI navigation actually still works after such a change, I judged the risk of a blind major-version migration to outweigh fixing a moderate-severity, non-RCE vulnerability (open redirect) that isn't yet under active exploitation. Left as a flagged, deferred item in `npm audit` output and LEGAL_REVIEW_NEEDED.md / a follow-up recommendation, for the user to do as its own tested task with real browser click-through afterward.

## Round 3: real installer bug fix, installer UX, and logo (this session)

### The actual bug behind "Docker Compose failed... container iii3xnz-backend-1 is unhealthy"
Root cause, confirmed from the user's real `docker logs iii3xnz-backend-1` output: `exec /usr/local/bin/iii3xnz-entrypoint: no such file or directory`. This is the classic signature of a Linux shell script with Windows (CRLF) line endings — the shebang line `#!/bin/sh` gets a trailing `\r`, so the kernel can't resolve the interpreter, even though the file is present. The script content itself (`backend/docker-entrypoint.sh`) was already correct LF in the committed git blob (confirmed in this sandbox), and its secret-generation design (random `JWT_SECRET`/`ENCRYPTION_KEY` written once into the shared `self_host_secrets` Docker volume, read by both `backend` and `worker`) was already sound. The corruption happens on **checkout**, not in storage: GitHub's `windows-latest` Actions runner (which builds the installer) defaults to `core.autocrlf=true`, silently rewriting the script to CRLF on disk before it gets packaged into the installer — and from there into every Docker image built on an end user's machine. This is a pre-existing bug in the original project, not something introduced by me this session; it was never caught earlier because this sandbox has no Docker to run the actual stack.

**Fix:** added `.gitattributes` at the repo root forcing LF line endings on `*.sh`, `Dockerfile*`, `docker-compose.yml`, and `*.conf`, regardless of the committer's or CI runner's OS/autocrlf setting. This is the standard, permanent fix for this class of bug — no code or script content needed to change, since the git-stored version was already correct.

### Installer UX: hiding the raw console
The Start Menu/Desktop/Run entries in `installer/iii3xnz.iss` launched `powershell.exe` with no window-hiding flag, so first run showed a raw PowerShell console scrolling through Docker build output — which reasonably looks alarming/unprofessional to a non-technical user and risks people abandoning the install. Fixed with two independent, low-risk layers:
1. Added `-WindowStyle Hidden` to all four PowerShell invocations in the `.iss` file (3 shortcuts + the post-install `[Run]` entry). This is a one-line, well-established flag with no logic change.
2. Added a small "please wait" WPF dialog (`Start-ProgressWindow`/`Stop-ProgressWindow` in `iii3xnz-launcher.ps1`) shown for the duration of the real setup work. Deliberately implemented as a **separate, simple child process** that knows nothing about Docker or the rest of the script — it just displays an indeterminate progress bar until a sentinel file is deleted (with a 20-minute safety timeout in case the parent ever exits uncleanly). This design was chosen specifically to avoid touching any of the already-working `Ensure-Docker`/`Read-OrCreateConfig`/`Start-Application` logic: the entire main flow is wrapped in a `try/finally` that starts and stops the window, with zero change to its internal order or behavior. `Show-Failure` also closes the progress window before showing its existing error dialog, so the two don't visually overlap. If the progress window ever fails to launch for any reason, it logs that and setup continues exactly as it did before this change — the dialog is cosmetic, never a dependency.

**Honest limitation: this WPF/PowerShell code could not be tested in this sandbox** — there is no Windows or PowerShell runtime available here. It was written carefully, reviewed line-by-line for correct here-string escaping (a well-known common source of bugs in this exact PowerShell pattern), and follows a widely-documented, standard idiom for showing WPF windows from PowerShell (the same `Add-Type -AssemblyName PresentationFramework` approach the pre-existing `Show-Failure` function already used successfully). It still needs a real run on Windows to confirm the dialog actually displays and closes as intended.
